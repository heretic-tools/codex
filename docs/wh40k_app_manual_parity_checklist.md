# WH 40K app manual parity checklist

Date: 2026-07-02

Scope: manual comparison of the official WH 40K app Battle Forge behavior
against the executable Builder parity fixtures.

This checklist exists because the installed WH 40K app exposes validation
concepts and data, but not a stable public command-line validator. The Builder
side of each case is executable in
`tests/builder_validation_wargear_parity_cases.test.mjs`; the official side must
be recreated in the app UI and recorded here.

Use the same baseline as `docs/wh40k_app_builder_parity_audit.md`:

- WH 40K app version: 2.0.3
- WH 40K app data version: 879
- Builder DB/data version: 879

Manual result fields:

- `WH app state`: `valid` or `invalid`.
- `WH app diagnostic`: the visible error category or shortest non-copyrighted
  paraphrase of the app message.
- `Parity`: `match`, `mismatch`, or `blocked`.

For wargear rows, prefer the generated worksheet from
`node HereticBuilder/tools/export_wargear_parity_manifest.mjs --format markdown`.
After filling the WH app result columns, run
`node HereticBuilder/tools/export_wargear_parity_manifest.mjs --check-results filled-results.md`
before copying the result back here. `--allow-pending` is allowed during an
in-progress pass but still fails on structural or state/parity mismatches.

For non-UI evidence rows, record the local guard command or data-source check in
`WH app method`; use `match` only when that guard directly compares against the
installed WH app DB/bundles or proves a static Builder export invariant.
For the 90-row minimum group table, generate a fresh worksheet with
`node HereticBuilder/tools/export_minimum_parity_manifest.mjs --format markdown`
and validate this checklist with
`node HereticBuilder/tools/export_minimum_parity_manifest.mjs --check-results docs/wh40k_app_manual_parity_checklist.md --allow-manual-pending-only`.
Drop `--allow-manual-pending-only` once every row has a real method/result/parity
value.
Current minimum-group status: 73 of 90 rows are guard-backed `match`; the
remaining 17 rows still require manual WH app UI/golden-case comparison. The 25
wargear parity case rows also remain pending until the generated wargear
worksheet is filled from the official app UI.
For the focused official app pass, use
`docs/wh40k_app_manual_pass_pack.md`. It is generated by
`node HereticBuilder/tools/export_manual_wh40k_pass_pack.mjs --format markdown`
and contains only the 17 remaining minimum manual UI cases plus the 26 wargear
UI setups. Use `docs/wh40k_app_manual_runbook.md` for the grouped WH app
execution order, `docs/wh40k_app_manual_status.md` for the generated
batch-progress view, `docs/wh40k_app_manual_next_action.md` for the generated
short workflow state, `docs/wh40k_app_manual_next_batch.md` for the generated
current-batch worksheet, and `docs/wh40k_app_manual_action_backlog.md` for the
generated list of logic/UI follow-ups after rows are triaged. Validate the pass
pack with
`node HereticBuilder/tools/export_manual_wh40k_pass_pack.mjs --check-results docs/wh40k_app_manual_pass_pack.md --allow-pending`
while the pass is in progress; drop `--allow-pending` when every row is filled.
In the pass pack, the `Action` column decides the follow-up owner:
`match -> none`, `mismatch -> logic|builder-ui`, and
`blocked -> official-ui-blocked|builder-ui`.
After filling that focused pack, derive the full minimum checklist with
`node HereticBuilder/tools/export_manual_wh40k_pass_pack.mjs --extract minimum-checklist --from docs/wh40k_app_manual_pass_pack.md`
and derive the wargear result worksheet with
`node HereticBuilder/tools/export_manual_wh40k_pass_pack.mjs --extract wargear-results --from docs/wh40k_app_manual_pass_pack.md`.
Generate the follow-up backlog with
`node HereticBuilder/tools/export_manual_wh40k_pass_pack.mjs --extract action-backlog --from docs/wh40k_app_manual_pass_pack.md`.
Generate the current pending batch sheet with
`node HereticBuilder/tools/export_manual_wh40k_pass_pack.mjs --extract next-pending-batch --from docs/wh40k_app_manual_pass_pack.md`.
Generate the short workflow state with
`node HereticBuilder/tools/export_manual_wh40k_pass_pack.mjs --next-action --from docs/wh40k_app_manual_pass_pack.md --format markdown`.
Check an in-progress or filled batch sheet with
`node HereticBuilder/tools/export_manual_wh40k_pass_pack.mjs --check-batch docs/wh40k_app_manual_next_batch.md --from docs/wh40k_app_manual_pass_pack.md --allow-pending`.
After filling that batch sheet, merge it back into a pass-pack candidate with
`node HereticBuilder/tools/export_manual_wh40k_pass_pack.mjs --merge-batch docs/wh40k_app_manual_next_batch.md --from docs/wh40k_app_manual_pass_pack.md > updated-pass-pack.md`.

Wargear rows are scoped to wargear validation only. Create each unit with the
`uiSetups` from `node HereticBuilder/tools/export_wargear_parity_manifest.mjs`;
if the WH app also shows unrelated Warlord, detachment, or roster-level errors,
satisfy or ignore those for the row and compare only the wargear diagnostic
family.

## Machine-readable wargear export

Use `node HereticBuilder/tools/export_wargear_parity_manifest.mjs` to produce a
JSON version of the executable 25-case wargear checklist. This output is meant
for repeatable comparison work: every case includes `comparisonScope:
"wargear-only"`, expected Builder state, validation codes, official-like
concept, `setupCount`, per-unit UI setup hints, unit rows, model rows, selected
option IDs, wargear item IDs, display names, and counts. Multi-unit cases can
intentionally become multiple WH app UI setups when their units belong to
different factions; the current 25 cases produce 26 UI setups. The matching
human-readable roster context table is
`docs/wh40k_app_wargear_ui_setups.md`. For direct WH app data entry, run
`node HereticBuilder/tools/export_wargear_parity_manifest.mjs --format markdown`
to include expected state, Builder validation codes, and selected wargear grouped
by model, plus `Pending` columns for WH app state, diagnostic, and parity. Once
those columns are filled, validate the worksheet with
`node HereticBuilder/tools/export_wargear_parity_manifest.mjs --check-results filled-results.md`.
Use `--allow-pending` only while a manual pass is incomplete.

## Comparison rule

Treat a case as `match` only when the official app and Builder agree on the
valid/invalid state and the diagnostic family. Exact wording does not need to
match; Builder intentionally keeps its own short UI text and stable internal
codes.
